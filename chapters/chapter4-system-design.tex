\chapter{System Design}
\label{chapter:system-design}
This chapter presents the technical design of the proposed system based on the requirements identified in Chapter \ref{chapter:system-analysis}. It describes the system architecture, database design, backend structure, and frontend organization that form the blueprint for the implementation discussed in Chapter \ref{chapter:implementation}.

\section{Design Overview}
\label{c4:section:design-overview}
The design follows a small set of guiding principles, each addressing one or more non-functional requirements identified previously. Table~\ref{tab:design-principles} summarizes these principles and their rationale.

\begin{table}[H]
	\centering
	\caption{Design Principles and Rationale.}
	\label{tab:design-principles}
	\begin{tabular}{|p{4.2cm}|p{9.8cm}|}
		\hline
		\textbf{Principle} & \textbf{Rationale} \\
		\hline
		
		Layered Architecture &
		Separates presentation, application programming interface (API), business logic, and data access concerns, improving maintainability and testability \cite{fowler2002peaa}. \\
		\hline
		
		Feature-Oriented Modular Design &
		Organizes code by business domain (e.g., Job, Application) rather than by technical type, keeping related logic together and easing future extension; modules are drawn around design decisions likely to change \cite{parnas1972criteria}. \\
		\hline
		
		Thin Controller, Rich Service &
		Controllers handle only request/response concerns; business logic and validation reside in services, reducing duplication and improving reusability, following the Service Layer pattern \cite{fowler2002peaa}. \\
		\hline
		
		Security by Design &
		Every access to a restricted resource is checked for authentication and authorization \cite{saltzer1975protection}, while credentials are stored as adaptive password hashes \cite{provos1999bcrypt, owasp_password_storage}. \\
		\hline
		
		Data Integrity &
		Relational constraints, foreign keys, and database integrity rules ensure data consistency and prevent invalid relationships \cite{codd1970relational}. \\
		\hline
		
	\end{tabular}
\end{table}

These principles are applied consistently across all modules of the system. They are illustrated in detail for the two featured modules, Job Application and Employer Job Management; the design of the remaining modules is documented in Appendix~\ref{appendix:supplementary-design}.

The remainder of this chapter is organized as follows. Section \ref{c4:section:system-architecture} presents the system architecture, including the C4-based container view. Section \ref{c4:section:database-design} details the database design and entity-relationship model for the featured modules. Section \ref{c4:section:backend-design} describes the backend design, including the layered structure and module organization. Section \ref{c4:section:frontend-design} covers the frontend design. Section \ref{c4:section:summary} summarizes the chapter.

\section{System Architecture}
\label{c4:section:system-architecture}
The system architecture is documented using the C4 model proposed by Simon Brown \cite{brown_c4}, which describes a software system at progressively narrower levels of zoom: Context, Container, and Component.

The System Context diagram identifies the system's boundary and its interactions with external actors, without describing internal structure.

As shown in Figure~\ref{diagram:c1-context}, four actors interact with the platform: the Guest browses for jobs without needing to authenticate, the Job Seeker applies for jobs, the Employer publishes and manages job postings, and the System Administrator moderates users and platform content.

\subsection{Container View}
The Container diagram decomposes the system into its major deployable units and shows how they communicate.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.75\linewidth]{diagrams/exported/C4/(NEW) C2-Container-Diagram-crop.pdf}
	\caption{Container Diagram.}
	\label{diagram:c2-container}
\end{figure}

As illustrated in Figure~\ref{diagram:c2-container}, the system consists of three containers:

\begin{itemize}
	\item The Frontend Web App is a React \cite{react_docs} single-page application (SPA) that renders the user interface (UI).
	\item The Backend API is a Node.js/Express service \cite{nodejs_docs, express_docs}, built with TypeScript \cite{typescript_docs} and the Prisma object-relational mapping (ORM) library \cite{prisma_docs}, that implements all business logic and exposes it as a Representational State Transfer (REST) API \cite{fielding2000rest}.
	\item The Database is a PostgreSQL \cite{postgresql_docs} instance that persists user accounts, job postings, applications, and other platform data.
\end{itemize}

The Frontend communicates with the Backend over Hypertext Transfer Protocol Secure (HTTPS) \cite{rfc9110} using JavaScript Object Notation (JSON) \cite{rfc8259}, and the Backend communicates with the Database using Structured Query Language (SQL) through Prisma.

\subsection{Component View: Frontend}
The Frontend component diagram decomposes the Frontend Web App container into its internal building blocks.

\begin{figure}[H]
	\centering

	\caption{Frontend Component Diagram.}

\end{figure}

As shown in Figure~\ref{diagram:c3-frontend}, the feature components are organized primarily by the roles they serve. Job Seeker, Employer, Back Office Worker functionality is grouped separately, while Job Discovery is shared across access contexts and can be used by both Guest and authenticated users.

Two shared components support the feature layers. The Application Shell and Router manages navigation and role-based access, while the Shared UI Kit provides reusable interface elements and common loading and error states.

Every feature component communicates with the backend exclusively through a centralized API Client, a generated software development kit (SDK) that wraps REST calls, injects the Bearer token, handles 401 interception, and parses responses. No feature component makes direct Hypertext Transfer Protocol (HTTP) requests; the API Client is the single outbound integration point.

\section{Database Design}
\label{c4:section:database-design}
The database design defines how the system's persistent data is organized and managed. It identifies the main business entities, their relationships, and the constraints that ensure data consistency. The design follows the principles introduced in Section~\ref{c4:section:design-overview}, particularly data integrity, by using a normalized relational schema with clearly defined primary and foreign key relationships \cite{codd1970relational}.

\subsection{Entity Relationship Overview}
Figure~\ref{diagram:erd-overview} presents an overview of the complete database schema used by the platform as an entity-relationship diagram (ERD) \cite{chen1976er}. To improve readability, the overview diagram includes the primary entities, key attributes, and relationships while omitting system-generated fields such as timestamps and audit metadata.

\begin{figure}[H]
	\centering
	\includegraphics[width=\linewidth]{diagrams/exported/ERD/Overview-ERD-crop.pdf}
	\caption{Entity Relationship Diagram.}
	\label{diagram:erd-overview}
\end{figure}

The remainder of this section details the entity groups that back the two featured modules - the company and job posting domain and the job application domain. The entities supporting the remaining modules are described in Appendix~\ref{appendix:supplementary-erd}.

\subsection{Company and Job Posting}
Figure~\ref{diagram:erd-company-job} details the entities involved in company and job posting management.

\begin{figure}[H]
	\centering
	\includegraphics[width=\linewidth]{diagrams/exported/ERD/Company-and-Job-Posting-ERD-crop.pdf}
	\caption{Company and Job Posting Entity Relationship Diagram.}
	\label{diagram:erd-company-job}
\end{figure}

An employer may own at most one company, and each company belongs to exactly one employer. Similarly, an employer may create multiple job postings, but each job posting is created by exactly one employer. Each job posting belongs to exactly one company, while a company may publish any number of job postings. The \texttt{status} attribute represents the current state of a job posting through the \texttt{JobStatus} enumeration.

\subsection{Job Application}
Figure~\ref{diagram:erd-job-application} details the entities involved in the job application workflow.

\begin{figure}[H]
	\centering
	\includegraphics[width=\linewidth]{diagrams/exported/ERD/Job-Application-ERD-crop.pdf}
	\caption{Job Application Entity Relationship Diagram.}
	\label{diagram:erd-job-application}
\end{figure}

A job seeker may upload multiple resumes and submit multiple applications, but each resume and each application belongs to exactly one job seeker. Each application is submitted for exactly one job posting, while a job posting may receive any number of applications. A resume may be attached to multiple applications, but each application references exactly one resume. The application's \texttt{status} attribute records where the application stands in the review process through the \texttt{ApplicationStatus} enumeration.

\subsection{Shared Backend Components}
\label{c4:subsection:shared-backend-components}
A small set of reusable infrastructure components is shared across all business modules, avoiding duplication and ensuring consistent behavior.

\begin{itemize}
	\item JWT Authentication: issues and verifies signed JWTs \cite{rfc7519} carrying the user's identifier and role, and is enforced through the \texttt{expressAuthentication} hook on protected routes.
	\item Role Guards: helpers such as \texttt{assertJobSeeker} and \texttt{assertEmployer} reject requests from users who lack the required role, applied as the first step of every service method. The guards are always paired with the tsoa \texttt{@Security} decorator to form defense in depth, a strategy of layering several independent safeguards so that a failure in one is caught by another \cite{nist2020sp80053}.
	\item HttpError: a uniform error type carrying an HTTP status and message, translated into the proper JSON error response.
	\item Prisma Client: the generated ORM client, instantiated once in \texttt{lib/prisma.ts} and imported by services for all database access.
	\item File Storage: abstracts file persistence behind a common interface, used for avatar and resume uploads.
	\item Email Service: wraps Nodemailer \cite{nodemailer_docs} to send transactional emails, such as password reset notifications.
	\item PasswordHasher and ResetTokenUtils: wrap bcrypt \cite{provos1999bcrypt} and token generation for credential handling and password recovery.
	\item AuditLogger: records a structured entry for a system event inside the same database transaction as the mutation it accompanies.
\end{itemize}

\subsection{Job Application Module}
\label{c4:subsection:job-application-module}
The Job Application Module lets job seekers apply to active job postings using one of their resumes, view their own submitted applications, and withdraw an application while it is still eligible. It resides in \texttt{api-external}, and every endpoint requires both a valid JWT and the \texttt{JOB\_SEEKER} role.

\subsubsection{Design Explanation}
Following the thin controller, rich service principle, \texttt{ApplicationController} exposes three REST endpoints and delegates each directly to a matching \texttt{ApplicationService} method, without containing business logic itself. This separation keeps HTTP adaptation concerns - request parsing, response shaping, and error mapping - distinct from the business rules that determine how an application can be created, listed, or withdrawn.

\texttt{ApplicationService} is the only class in the module that owns business logic and the only class that accesses the database, doing so through the shared Prisma Client. It operates on the User, Job, Resume, and Application entities whose relationships are detailed in Figure~\ref{diagram:erd-job-application}. The service depends on two shared infrastructure components: \texttt{AssertRole}, and \texttt{AuditLogger}. These components are documented in Section~\ref{c4:subsection:shared-backend-components}.

Authentication and role authorization are enforced at two levels. At the controller boundary, tsoa's \texttt{@Security("jwt", ["JOB\_SEEKER"])} decorator causes the framework to verify the JWT and confirm the caller's role before the controller method is entered. The service then re-asserts the same role via \texttt{AssertRole}, providing defense in depth: business methods remain protected regardless of how they are invoked. Each service method corresponds to a single use case described in Chapter~\ref{chapter:system-analysis}.

\label{c4:subsection:employer-job-module}

\subsubsection{Design Explanation}
The Employer Job Management Module is decomposed into three cohesive controller and service pairs, each owning a distinct subdomain of the employer workflow.
\begin{itemize}
	\item \texttt{EmployerCompanyController} and \texttt{EmployerCompanyService} handle company profile management.
	\item \texttt{JobManagementController} and \texttt{JobManagementService} manage the lifecycle of job postings.
	\item \texttt{EmployerApplicationController} and \texttt{EmployerApplicationService} cover the review of incoming applications.
\end{itemize}
This separation keeps each pair focused on a single business concern and allows it to evolve independently.

Across all three pairs the same structural pattern is applied: each controller is annotated with tsoa's \texttt{@Security("jwt", ["EMPLOYER"])} decorator at the class level, while exposing REST endpoints and delegating each directly to a matching service method. Each service is the sole owner of business rules and the only class in its pair that accesses the database through the shared Prisma Client. Every service method depends on \texttt{AssertRole} and \texttt{AuditLogger}, which are described in Section~\ref{c4:subsection:shared-backend-components}.

Company Profile Management takes no company identifier in its operations because the employer-company relationship is one-to-one: the owning employer is resolved from the authenticated user. Job Posting Management's own methods can only move a posting into \texttt{PENDING\_APPROVAL}, \texttt{CLOSED}, or \texttt{DELETED}, so a posting cannot become publicly visible without first passing through this external moderation gate. Employer Application Management exposes operations for the employer-driven status transitions that complement the job-seeker-initiated \texttt{SUBMITTED} and \texttt{WITHDRAWN} transitions defined in the Job Application Module. Together the three pairs implement the complete round trip of a recruitment event studied in Chapter~\ref{chapter:system-analysis}.


\section{Frontend Design}
\label{c4:section:frontend-design}

The frontend is a React SPA. Pages are grouped in feature folders that mirror the backend module structure, so a feature can be traced end to end.

\subsection{Frontend Structure and Shared Components}
\label{c4:subsection:frontend-structure}

Each feature module under \texttt{ui-external/} follows the same internal shape: page-level components sit directly in the module's folder, and any component used only within that module is placed in a nested \texttt{components/} folder beneath it. For example, the Job Application module is organized as follows:

\dirtree{%
	.1 ui-external/applications.
	.2 ApplyJobPage.tsx.
	.2 MyApplicationsPage.tsx.
	.2 components.
	.3 ApplicationCard.tsx.
	.3 ApplicationStatusBadge.tsx.
	.3 ResumeSelector.tsx.
}
The same structure is applied to the Employer Job Management UI and other feature modules. Shared interface elements are provided through the common UI layer and reused across feature components rather than being duplicated within individual modules. The project uses shadcn/ui \cite{shadcn_docs} and Tailwind CSS \cite{tailwind_docs} for these reusable interface elements.

\subsection{Job Application UI}
The Job Application UI follows the feature structure described above. Its page-level components are separated according to the two primary application workflows: applying for a job and managing submitted applications. Reusable elements specific to these workflows, such as application cards, status indicators, and resume selection, are kept within the feature's \texttt{components/} directory.

Components are implemented as \texttt{.tsx} files, keeping their rendering logic and component-specific styling together. This convention keeps each UI component self-contained and avoids unnecessary separation between files that belong to the same component.

\subsection{Employer Job Management UI}

The Employer Job Management UI applies the same feature-based organization to the employer workflows. Page-level components handle the major job-management and company-profile screens, while reusable elements are colocated within their respective feature directories.

The UI reuses shared components and the centralized API Client for common interface and backend-integration concerns. This keeps the employer-specific UI focused on its feature responsibilities while avoiding duplication of shared frontend functionality.

\section{Summary}
\label{c4:section:summary}

This chapter presented the technical design of the platform. The system follows a layered, feature-oriented architecture split into a React frontend, a Node.js/Express API, and a PostgreSQL database. The database design centered on the entity groups that serve the two featured modules: company and job posting, and job application. The backend design introduced the project structure, the shared infrastructure components, and the class-level design of the Job Application and Employer Job Management modules. The frontend design described the page structure for both featured modules. The next chapter describes how this design was realized in code.
